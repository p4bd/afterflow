# AfterFlow 项目复盘与 Bad Case

所有案例来自历史真实模型记录、自动化测试或隔离故障注入，不是线上事故。历史原始记录见 `docs/evidence/closeout/historical-agent/`。

### BC-001：金额争议未建案
- 来源：真实模型运行，2026-09-15，AGENT-007（2/3 未建案）。
- 输入与前置状态：`ORDER-1001 的退款金额不对，少退了`，Mock 订单。
- 预期与实际：应先持久化 Case 再取证；实际继续解释但没有 Case、Action 或副作用。
- 影响范围：聊天 Agent 入口可能丢失可恢复上下文；网页 intake 不受影响。
- 最小复现：离线查看 historical-agent JSONL 中 AGENT-007。
- 定位证据：工具轨迹与精确 thread 查询均无 Case；不是评分器扫描上限导致。
- 根因：SOP 的“先建案”是模型可选择指令，不是聊天入口硬约束。
- 修复：评测按无 Case 失败并立即落盘；生产网页继续采用先持久化的确定性 intake。未偷偷在评分后补案。
- 验证：历史重算保持 2 次失败；新真模型复测未执行。
- 剩余限制：聊天入口尚未强制预建案，达到可接受成功率前不把它作为唯一受理入口。

### BC-002：歧义订单被模型选中
- 来源：真实模型运行，AGENT-009；一次未建案、一次错选 ORDER-1001。
- 输入与前置状态：用户明确说不确定 ORDER-1001 或 ORDER-1002。
- 预期与实际：应保存待澄清 Case，实际把模型显式参数当事实。
- 影响范围：可能对错误订单形成后续方案；历史记录未证明发生资金副作用。
- 最小复现：`test_model_supplied_fields_cannot_resolve_ambiguous_or_missing_claims`。
- 定位证据：确定性提取可识别多个订单，覆盖发生在 Tool 参数进入共享 intake 时。
- 根因：模型提取值和可信 UI 确认值没有来源区分。
- 修复：`structured_source=model` 时以原文确定性提取为边界，歧义/缺失不能被模型参数填满。
- 验证：修复前会得到 decided，修复后 order/issue 均为空且 awaiting_clarification；18 条 intake/tool 回归通过。
- 剩余限制：长文本和复杂否定仍需真模型留出集验证。

### BC-003：只有订单却自行补成丢件
- 来源：真实模型运行，AGENT-012，2/3 被补成未收到且调用创建 Action。
- 输入与前置状态：只说 `想处理售后，订单是 ORDER-1001`。
- 预期与实际：应询问具体问题，实际推断问题并进入写路径。
- 影响范围：错误业务事实可能形成审批待办。
- 最小复现：评分器反例 `test_missing_issue_with_created_action_fails_side_effect_score`。
- 定位证据：旧评分把字段合并且未检查禁止工具；新评分单列 issue、禁止工具和持久化 Action。
- 根因：输入边界与评分合同都没有把“未知”当一等状态。
- 修复：共享 Action 入口要求 Case 为 decided 且有决策；模型字段不能补齐原文缺失；fixture 标注禁止工具/Action。
- 验证：评分器反例通过；当前真实 18×3 中该任务禁止 Tool 3/3 未调用、禁止 Action 3/3 未产生，但仍有 2/3 次没有持久化 Case。
- 剩余限制：历史轨迹没有 Action 快照，持久化副作用指标记不可用。

### BC-004：跨用户与并发幂等穿透
- 来源：隔离 HTTP 测试；不是线上事故。
- 输入与前置状态：Alice/Bob 使用相同 key；同用户两个并发首次请求。
- 预期与实际：旧实现可能回放他人响应，且 callback 可执行两次。
- 影响范围：数据泄露与重复写；资金路径另有业务键但不能替代请求隔离。
- 最小复现：`tests/test_after_sales_router_idempotency.py`。
- 定位证据：旧键仅 endpoint+key，且顺序为 lookup→callback→store。
- 根因：身份检查在 callback 内，缓存命中在其之前；唯一约束发生在副作用之后。
- 修复：缓存作用域加入可信 actor/role/resource，单进程按 key 串行；全部写入口复用 helper。
- 验证：跨用户、并发、body 冲突、intake/supplement/action/approve/execute 回放均通过。
- 剩余限制：多 worker 仍需数据库 claim；HTTP TTL 与长期业务幂等必须分开。

### BC-005：退款已执行但 Action 首次落库失败
- 来源：自动化故障注入，2026-09-15。
- 输入与前置状态：已审批、已预留退款；Provider 成功后 `save_action` 抛错。
- 预期与实际：旧重试先看剩余预留并报余额变化，无法恢复；外部交易已存在。
- 影响范围：案件卡住，盲目重试还可能造成双退风险。
- 最小复现：`test_shared_execution_recovers_after_provider_success_and_repository_failure`。
- 定位证据：Mock 交易数为 1、预留归零、Action 未保存。
- 根因：恢复查询排在新执行前置条件之后。
- 修复：校验身份/载荷后先按业务键核对既有 Provider 结果，再决定是否需要余额检查和新副作用。
- 验证：首次失败、第二次恢复、交易数仍为 1、Case 进入 processing；15 条 Action 回归通过。
- 剩余限制：Mock 账本进程内，未证明跨进程对账或 exactly-once。

### BC-006：补发决策后库存变化
- 来源：代码审查与自动化测试。
- 输入与前置状态：决策时有库存，执行前库存被其他请求耗尽。
- 预期与实际：旧 Mock dispatch 不拥有库存，仍会返回成功凭证。
- 影响范围：演示可报告不存在的出库；真实 OMS 未接入。
- 最小复现：`test_reverse_executor_is_idempotent_by_key`。
- 定位证据：决策读取静态 INVENTORY，旧执行器仅维护 outbound map。
- 根因：把决策快照误当执行时权威状态。
- 修复：执行器锁内按 SKU 重查/扣减；先查业务键，回放不二次扣减。
- 验证：库存 1 首次成功并归零，同 key 回放成功，新 key 被拒绝；13 条相关回归通过。
- 剩余限制：仅 Mock 单进程库存，不代表真实仓储并发保证。

## 反复问题与设计取舍

“有模块、有测试但未接主链路”来自过度验证构造结果，而非真实入口。改进方式是从 HTTP/Tool 共用入口写故障窗口测试，并验证 Runtime middleware 真能由配置构造。

Agent 负责理解歧义、选择只读工具和沟通；Tool 提供窄合同；确定性引擎负责金额、资格、风险和状态转换；Skill 约束步骤但不能替代服务端校验。真实失败说明把未知字段交给模型猜，会把语言错误升级成资金风险。

数据库与外部 Provider 无法共用事务，因此不声称 exactly-once。当前是 at-least-once 请求加业务键查询：未知结果先核对，再补内部状态。真实网关还需要持久查询 API、Webhook 和人工对账队列。

旧评估会误导，是因为“字段”合并、只看回复草稿、把脚本未异常叫成功、共享状态且缺 Action/账本。新口径分层、分母明确、失败保留、运行隔离并对缺失证据返回不可用。

性能只优化有测量证据的瓶颈：审批列表 N+1 改为单 JOIN；Agent 通过显式领域路由、Skill 白名单和复合建案快照复用，将同任务平均 Tool 2.20→1.28、p95 11.64→6.35 秒、平均 Token -22.0%，严格完成率 72.2%→100%。SQLite、单进程与轮询在演示规模仍足够；换 PostgreSQL 不能自动解决 Mock 账本、多实例 claim 或 Agent 质量。

若重做：先固定真实输入与评分合同，再做最小 Case 闭环；随后定义幂等/恢复不变量；之后才接 UI 和真模型；最后根据 Bad Case 与剖析做定向优化。

## 当前限制与升级条件

- Mock OMS/支付/物流 → 不能证明真实对账与外部幂等 → 当前只做业务键回放与人工阻塞 → 接入真实沙箱且故障注入通过后升级声明。
- 单进程内存账本/SQLite → 重启和多实例结果不确定 → 文档明确边界 → 出现多 worker 或需无人工恢复时持久化账本与 DB claim。
- 长文本、否定、歧义泛化有限 → 可能误抽取 → 未知值 fail-closed、18 任务开发/留出集 → 有匿名真实样本和专家标注后扩集。
- 图片与退货质检人工 → 退货路径不能自动闭环 → 缺收货/质检即拒绝执行 → 接入可信仓库事件或视觉验收后升级。
- 任务集小且金标准来自规则 → 不能证明行业最优 → 报告分母与来源 → 有独立专家标注后做一致性评审。
- 运营告警使用 Mock 分母 → 不能推出真实经营改善 → 仅演示指标算法 → 接入真实订单量并做时间窗回测后再谈收益。
